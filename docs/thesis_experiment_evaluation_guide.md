# AI 助教系统实验评估指南

本文档用于指导毕业论文实验评估章节的设计与执行，重点回答以下问题：

- 实验资料从哪里来
- 问题集如何构造
- 检索质量和生成质量怎么评估
- baseline 如何设置
- 指标如何解释
- 如果系统效果不如普通方法，应该如何对比和写作

## 1. 实验目标

本系统的实验评估不应只证明“模型能回答问题”，而应重点验证课程知识库 AI 助教系统在以下方面是否有效：

1. 能否从课程资料中检索到正确证据。
2. 能否基于证据生成准确、可读、可追溯的回答。
3. 使用 RAG、重排序、查询改写、知识图谱等模块后，是否相比基础方法有改进。
4. 系统在真实部署环境下是否具有可接受的响应时间和稳定性。

因此，实验应分为四类：

| 实验类型 | 主要目的 |
|---|---|
| 检索质量评估 | 判断系统能否找到正确资料片段 |
| 生成质量评估 | 判断回答是否正确、完整、可读、可溯源 |
| 消融实验 | 判断各个模块是否带来增益 |
| 性能与稳定性评估 | 判断系统是否可实际运行 |

## 2. 实验资料来源

建议使用开放课程资料或自己整理的课程资料，避免版权风险。

### 2.1 推荐资料来源

| 来源 | 适用场景 | 说明 |
|---|---|---|
| OpenStax 开放教材 | 概念解释、事实查询、教材型问答 | 免费开放教材，适合构造课程知识库 |
| MIT OpenCourseWare | 课程讲义、作业、考试题 | 公开课资料丰富，适合综合问答 |
| 学校课程资料 | 最贴近毕设应用场景 | 若用于论文，需要确认是否允许使用 |
| 自己整理的讲义 | 最容易标注标准答案和来源 | 适合小规模可控实验 |

不建议把通用开放域问答数据集作为主实验数据，例如 HotpotQA、MS MARCO、BEIR 等。它们可以作为补充实验，但它们不完全符合“课程知识库 AI 助教”的业务场景。

### 2.2 推荐资料规模

本科毕业设计不需要做特别大的数据集，建议控制在可人工检查的规模：

| 资料类型 | 建议数量 |
|---|---:|
| PDF 教材或讲义 | 3-5 个 |
| PPT 课件 | 3-10 个 |
| Word/Markdown/TXT 资料 | 5-10 个 |
| 图片或截图资料 | 5-20 张 |
| 总问题数 | 50-100 个 |

如果时间紧，最低可使用 30-50 个问题，但应覆盖不同问题类型。

## 3. 问题集构造方法

每个评测问题都应尽量有“标准来源”，即这个问题的答案应该能从某个课程资料中找到。

### 3.1 问题类型设计

建议按以下类型构造问题：

| 问题类型 | 数量建议 | 作用 |
|---|---:|---|
| 事实查询 | 20 | 测试系统能否定位明确知识点 |
| 概念解释 | 20 | 测试回答是否准确、清晰 |
| 对比分析 | 10-15 | 测试系统能否整合多个相近概念 |
| 推理应用 | 10-15 | 测试系统能否基于资料进行简单推理 |
| 跨章节综合 | 5-10 | 测试多资料检索能力 |
| 多模态资料问题 | 5-10 | 测试图片、课件截图等资料理解能力 |

### 3.2 问题来源

问题可以来自：

1. 教材章节后的复习题。
2. 课程作业或考试题。
3. 根据课程资料人工编写。
4. 使用大模型辅助生成，再由人工审核和修正。

推荐流程是：先选定资料章节，再让大模型根据章节生成候选问题，最后人工检查问题是否合理、答案是否能在资料中找到、标准来源是否明确。

### 3.3 标注格式

项目中已有 benchmark 模板：

```text
backend/tests/fixtures/benchmark/benchmark_spec_template.json
```

可以复制一份，例如：

```text
backend/tests/fixtures/benchmark/thesis_benchmark_spec.json
```

格式如下：

```json
{
  "questions": [
    {
      "id": "q1",
      "text": "TCP 慢启动的作用是什么？",
      "expected_source_names": ["network_notes.pdf"],
      "expected_chunk_ids": [],
      "expected_doc_ids": []
    }
  ]
}
```

其中：

- `text` 是评测问题。
- `expected_source_names` 是预期应命中的资料文件名。
- `expected_chunk_ids` 可以先不填，除非已经能稳定拿到 chunk id。
- `expected_doc_ids` 可以先不填。

本科论文阶段建议优先标注 `expected_source_names`，实现成本低，也足够支撑 Recall@K、nDCG@K、MRR 等检索指标。

## 4. Baseline 设置

baseline 不一定要找外部系统。对本系统而言，最有价值的 baseline 是“逐步关闭模块”的内部对比。

### 4.1 推荐 baseline

| 实验组 | 配置 | 目的 |
|---|---|---|
| No RAG | 不使用课程资料检索，直接由生成模型回答 | 验证课程知识库是否有价值 |
| Basic RAG | 只使用向量检索 + 生成 | 作为基础 RAG baseline |
| RAG + Reranker | 向量检索后加入重排序 | 验证 reranker 是否提高证据质量 |
| Full System | RAG-Anything + Qdrant + Neo4j + Reranker + Query Rewrite | 当前完整系统效果 |

当前系统的完整配置大致为：

```text
生成模型：gpt-5.4
实体关系抽取模型：Qwen/Qwen2.5-7B-Instruct
VLM 模型：Qwen/Qwen3-VL-8B-Instruct
嵌入模型：BAAI/bge-m3
重排序模型：BAAI/bge-reranker-v2-m3
向量数据库：Qdrant
图数据库：Neo4j
RAG 引擎：RAG-Anything / LightRAG
```

### 4.2 如果系统效果比普通方法差，应该和什么比

如果完整系统效果没有明显超过普通方法，不要只写“效果不好”。应该进一步拆开比较，找到原因。

推荐对比顺序：

1. **Full System vs No RAG**
   - 如果 Full System 仍然比 No RAG 好，说明知识库检索仍然有效。
   - 即使没有超过所有 baseline，也可以证明系统降低了无依据回答。

2. **Full System vs Basic RAG**
   - 如果 Full System 不如 Basic RAG，可能是图谱检索、查询改写或复杂解析引入了噪声。
   - 论文中可以分析复杂模块在小规模课程资料上的收益有限。

3. **RAG + Reranker vs Basic RAG**
   - 如果加入 reranker 后变差，可能是重排序模型与课程领域不匹配，或召回候选数量太少。

4. **不同问题类型分组比较**
   - 系统可能在事实查询上优势不明显，但在跨章节综合、多模态问题或需要溯源的问题上更好。
   - 这类结果依然有论文价值。

5. **生成质量 vs 检索质量分开看**
   - 检索差：说明没有找到正确资料。
   - 检索好但生成差：说明模型没有正确利用证据。
   - 生成看似流畅但溯源差：说明有幻觉风险。

论文中可以这样写：

> 实验结果显示，完整系统在部分简单事实型问题上相较基础 RAG 提升有限，主要原因是该类问题的答案通常集中在单一资料片段中，基础向量检索已经能够较好召回相关内容。但在跨章节综合问题、多资料证据整合问题和需要引用溯源的问题中，完整系统在引用可追溯率、回答完整性和低置信触发审核方面表现更稳定，说明复杂 RAG 流程更适合面向课程知识库的教学问答场景。

## 5. 检索质量评估

检索质量关注“系统有没有找对资料”。

### 5.1 推荐指标

| 指标 | 含义 | 越大/越小 |
|---|---|---|
| Recall@K | 前 K 个结果中覆盖正确资料的比例 | 越大越好 |
| nDCG@K | 正确资料是否排在更靠前的位置 | 越大越好 |
| MRR | 第一个正确结果出现得有多靠前 | 越大越好 |
| 平均来源数 | 每次回答引用的证据数量 | 适中较好 |
| 检索延迟 | 完成一次检索消耗的时间 | 越小越好 |

### 5.2 指标解释

如果 `Recall@5` 高，说明系统大概率能把正确资料召回。

如果 `nDCG@5` 高，说明正确资料不仅被召回，而且排序靠前。

如果 `MRR` 高，说明第一个正确结果通常出现在前几位，生成模型更容易使用正确证据。

如果 Recall 高但生成质量差，问题通常不在检索，而在证据利用或生成模型。

如果 Recall 低，则需要优先检查资料解析、切分、embedding、query rewrite 和检索参数。

## 6. 生成质量评估

生成质量关注“回答本身好不好”。

建议采用人工评分，评分范围 1-5 分。

| 指标 | 说明 |
|---|---|
| 正确性 | 回答是否符合课程资料 |
| 完整性 | 是否覆盖问题需要的关键点 |
| 相关性 | 是否紧扣学生问题 |
| 可读性 | 是否表达清楚、适合教学场景 |
| 溯源性 | 回答内容是否能对应引用资料 |
| 幻觉情况 | 是否出现资料中没有或明显错误的内容 |

评分表可以设计为：

| 问题编号 | 方法 | 正确性 | 完整性 | 相关性 | 可读性 | 溯源性 | 是否幻觉 |
|---|---|---:|---:|---:|---:|---:|---|
| q1 | No RAG | 3 | 3 | 4 | 5 | 1 | 是 |
| q1 | Full System | 5 | 4 | 5 | 5 | 5 | 否 |

最后统计：

```text
平均正确性 = 所有问题正确性得分平均值
平均完整性 = 所有问题完整性得分平均值
平均溯源性 = 所有问题溯源性得分平均值
幻觉率 = 出现明显错误或无依据内容的问题数 / 总问题数
引用可追溯率 = 引用能对应正确资料的问题数 / 总问题数
```

## 7. 系统性能评估

系统性能用于说明系统能否稳定运行。

推荐统计：

| 指标 | 含义 |
|---|---|
| 查询成功率 | 成功返回回答的比例 |
| 主链成功率 | RAG 主流程成功完成的比例 |
| fallback 率 | 进入降级逻辑的比例 |
| 平均置信度 | 系统对回答质量的平均估计 |
| P95 延迟 | 95% 请求能在该时间内完成 |
| 平均延迟 | 平均响应时间 |

这些指标可以从系统已有接口中获得：

```text
GET /api/v1/admin/rag-performance
GET /api/v1/admin/rag-ablation
GET /api/v1/admin/experiment-results
```

也可以直接运行项目已有脚本导出报告。

## 8. 如何运行项目已有评估脚本

项目已有离线 benchmark 脚本：

```text
backend/scripts/run_research_benchmark.py
```

运行方式：

```bash
cd backend
python scripts/run_research_benchmark.py \
  --days 30 \
  --benchmark-spec tests/fixtures/benchmark/thesis_benchmark_spec.json \
  --retrieval-k 5
```

输出目录：

```text
backend/runtime_tmp/experiment_reports/
```

输出内容包括：

- JSON 报告
- Markdown 报告
- query success rate
- Recall@K
- nDCG@K
- MRR
- RAG performance
- RAG ablation
- experiment results

如果要做 baseline 对比，可以先跑一次 baseline，保存生成的 JSON 报告，然后跑当前系统并指定 baseline：

```bash
cd backend
python scripts/run_research_benchmark.py \
  --days 30 \
  --benchmark-spec tests/fixtures/benchmark/thesis_benchmark_spec.json \
  --retrieval-k 5 \
  --baseline-report runtime_tmp/experiment_reports/benchmark_xxx.json
```

## 9. 建议实验流程

推荐按以下步骤执行：

1. 选择 3-5 份课程资料。
2. 上传资料到系统知识库，并等待解析和索引完成。
3. 人工构造 50-100 个问题。
4. 为每个问题标注预期来源文件名。
5. 运行 Basic RAG baseline。
6. 运行 RAG + Reranker。
7. 运行 Full System。
8. 导出自动指标报告。
9. 对每组回答进行人工评分。
10. 汇总检索指标、生成指标和性能指标。
11. 按问题类型分析系统在哪些场景有效，在哪些场景不足。

## 11. 技术栈有效性专项实验

为了更清楚地证明本系统技术栈的有效性，不建议只做总体准确率对比。总体准确率容易掩盖系统在复杂资料、多模态解析、知识关系组织和可溯源回答上的优势。更推荐围绕本系统的核心技术点设计专项实验。

### 11.1 表格与复杂版面识别实验

本系统使用 RAG-Anything、MinerU 和 VLM 处理复杂文档版面，因此应单独设计表格、公式、图文混排类问题。普通 RAG baseline 可以设置为 Text-only RAG，即只抽取 PDF/PPT 中的普通文本，不使用 MinerU、VLM 和结构化表格解析。

| 方法 | 配置 |
|---|---|
| Text-only RAG | 普通文本抽取 + 文本切块 + 向量检索 |
| Full System | RAG-Anything + MinerU + VLM + 当前检索链路 |

实验资料应包含：

| 资料类型 | 内容要求 |
|---|---|
| PDF 教材 | 包含表格、公式、对比表 |
| PPT 课件 | 包含流程图、参数表、实验结果表 |
| 图片截图 | 包含表格截图、图示说明或公式截图 |

问题示例：

| 问题类型 | 示例 |
|---|---|
| 单元格查询 | 表 2 中 TCP 和 UDP 在可靠性方面的区别是什么？ |
| 行列关系查询 | 根据实验结果表，哪种算法的准确率最高？ |
| 数值比较 | 表格中延迟最低的方法是哪一个？ |
| 表格综合 | 根据表中三个指标，哪种方案整体表现最好？ |

推荐指标：

| 指标 | 说明 |
|---|---|
| 表格问题准确率 | 回答是否正确读取表格内容 |
| 表格证据命中率 | citation 是否指向包含表格的资料 |
| 数值错误率 | 是否读错数字、单位、行列 |
| 引用可追溯率 | 答案是否能追溯到表格所在页面或文件 |

如果 Full System 在该组实验中优于 Text-only RAG，可以说明复杂文档解析和多模态理解模块有效。

### 11.2 多模态资料问答实验

该实验用于证明 VLM 和多模态预处理能力。普通 RAG 通常只能处理文本，对图片、课件截图、图表和公式理解能力弱。

| 方法 | 配置 |
|---|---|
| Text-only RAG | 忽略图片，仅使用文档文本 |
| OCR/Text RAG | 对图片做简单 OCR 后入库 |
| Full System | 使用 VLM 理解图片、截图、公式和图表 |

问题示例：

| 类型 | 示例 |
|---|---|
| 图片内容识别 | 这张流程图中数据预处理之后的步骤是什么？ |
| 公式理解 | 图中公式里的参数 lambda 表示什么？ |
| 图表理解 | 根据柱状图，哪一组实验结果最高？ |
| PPT 截图理解 | 课件截图中列出的三个核心模块是什么？ |

推荐指标：

| 指标 | 说明 |
|---|---|
| 多模态问题准确率 | 图片、公式、图表问题答对比例 |
| 视觉证据命中率 | 是否引用了正确图片或课件页 |
| 关键信息覆盖率 | 是否提到了图中关键文字、数值、步骤 |
| 幻觉率 | 是否编造图中没有的信息 |

### 11.3 知识图谱与实体关系实验

本系统使用实体关系抽取模型和 Neo4j 存储知识关系。该能力不一定在简单事实题上体现明显，更适合通过关系型问题验证。

| 方法 | 配置 |
|---|---|
| Vector RAG | 只用向量相似度检索 |
| Vector RAG + Reranker | 向量检索后重排序 |
| Full System | 向量检索 + 实体关系抽取 + 图数据库 |

问题示例：

| 类型 | 示例 |
|---|---|
| 前置关系 | 学习拥塞控制之前需要掌握哪些概念？ |
| 概念关系 | 滑动窗口协议和流量控制之间是什么关系？ |
| 依赖关系 | 为什么理解子网划分需要先理解 IP 地址结构？ |
| 综合关系 | TCP 可靠传输涉及哪些机制，它们之间如何配合？ |

推荐指标：

| 指标 | 说明 |
|---|---|
| 关系问题准确率 | 是否正确回答实体之间的关系 |
| 关键实体覆盖率 | 回答中是否包含应出现的核心概念 |
| 关系完整性评分 | 是否说清楚依赖、包含、因果或对比关系 |
| 跨片段证据命中率 | 是否能引用多个相关资料片段 |

如果图谱增强后的整体准确率没有显著提升，也可以分析其在关系型问题、跨章节问题中的局部收益。

### 11.4 重排序与查询改写实验

该实验用于证明 reranker 和 query rewrite 对检索排序质量的影响。此类模块的效果通常不只体现在最终回答准确率，也体现在 nDCG@K 和 MRR 上。

| 方法 | 配置 |
|---|---|
| Basic RAG | bge-m3 向量召回 |
| Basic RAG + Reranker | 向量召回后使用 bge-reranker-v2-m3 重排序 |
| Basic RAG + Query Rewrite | 查询改写后再检索 |
| Full System | Query Rewrite + Reranker + 完整 RAG 链路 |

问题应尽量模拟学生真实提问，例如：

| 问题 | 特点 |
|---|---|
| 这个窗口机制到底是干嘛的？ | 表述模糊 |
| 为什么这个协议会丢包还可靠？ | 口语化 |
| 老师说的那个慢启动是啥？ | 关键词不完整 |
| 这两个算法哪个更好？ | 需要上下文和改写 |

推荐指标：

| 指标 | 说明 |
|---|---|
| Recall@5 | 是否召回正确资料 |
| nDCG@5 | 正确资料排序是否靠前 |
| MRR | 第一个正确结果出现的位置 |
| 回答准确率 | 最终回答是否正确 |
| 平均延迟 | 模块增强带来的时间成本 |

### 11.5 幻觉控制与可溯源实验

教学系统不仅要回答正确，还要能说明依据。该实验用于证明 RAG、citation、confidence 和审核机制的价值。

| 方法 | 配置 |
|---|---|
| LLM Only | 直接使用生成模型回答 |
| Basic RAG | 普通向量 RAG |
| Full System | 完整系统，带 citation、confidence 和审核机制 |

问题设计：

| 类型 | 说明 |
|---|---|
| 资料内问题 | 答案明确存在于课程资料中 |
| 资料外问题 | 课程资料中没有答案 |
| 易混淆问题 | 问法相近但概念不同 |
| 诱导型问题 | 问题中包含不一定成立的前提 |

推荐指标：

| 指标 | 说明 |
|---|---|
| 幻觉率 | 出现无依据或错误回答的比例 |
| 拒答/提示不足率 | 资料不足时是否说明无法确定 |
| 引用可追溯率 | 回答是否有正确来源 |
| 低置信触发率 | 不确定问题是否进入审核或提示 |
| 答案忠实度 | 回答是否严格依据资料 |

## 12. 结果分析写作建议

如果实验结果较好，可以重点写：

1. RAG 相比 No RAG 降低了幻觉率。
2. Reranker 提升了 nDCG@5 和 MRR。
3. 完整系统在跨章节综合问题上更有优势。
4. 引用可追溯率提高，适合教学场景。

如果实验结果一般，可以重点写：

1. 系统在简单事实题上与 Basic RAG 差距不大，因为简单问题不需要复杂图谱推理。
2. 完整系统在延迟上高于基础方法，这是多阶段解析、检索和重排序带来的代价。
3. 系统优势更多体现在可追溯、可审核、多模态接入和教学闭环，而不仅是单次问答准确率。
4. 当前评测数据规模有限，复杂模块的优势需要在更大规模课程资料和更多跨资料问题中进一步验证。

可以使用如下表述：

> 从实验结果看，完整系统在简单事实型问题上的提升有限，但在跨章节综合问题和需要引用溯源的问题上表现更稳定。相比无 RAG 方法，系统能够显著提高回答的可追溯性，并降低无依据回答的比例。相比基础 RAG 方法，完整系统引入了重排序、查询改写和图谱存储，虽然带来一定延迟开销，但为课程知识库场景提供了更完整的证据组织和审核回流能力。

## 13. 最小可执行方案

如果时间有限，最低限度完成以下内容即可支撑毕业论文实验章节：

1. 准备 3 份课程资料。
2. 构造 50 个问题。
3. 标注每个问题的预期来源文件。
4. 对比 No RAG、Basic RAG、Full System 三组。
5. 统计 Recall@5、nDCG@5、MRR。
6. 人工评分正确性、完整性、溯源性。
7. 统计幻觉率、平均延迟和查询成功率。

这套实验能证明系统是否真正利用课程资料、回答是否可追溯、复杂 RAG 流程是否有实际收益。
